# Optional User Repo CI Scaffold

## Purpose

This document defines whether, and how, `spec-injector` may provide an opt-in GitHub Actions CI scaffold in a user repository in the future.

This is not CI for the `spec-injector` repository itself.

This design only discusses whether a target/user repository initialized by `spec-injector` may optionally create `.github/workflows/spec-injector.yml`.

The goals are to:

- Keep `spec init` low-intrusion by default.
- Avoid modifying a user repository's `.github/workflows` by default.
- Let users who need a CI gate opt in.
- Keep CLI behavior deterministic.
- Avoid interfering with a user's existing CI, branch protection, or language stack.

## Current state

- The `spec-injector` repository already has CI.
- CI runs `pnpm test`.
- `pnpm test` covers core CLI commands.
- `spec init` currently creates only `.spec-injector/config.json` and `.spec-injector/.gitignore`.
- `spec init` currently does not create `.github/workflows`.
- User repo CI scaffold is not implemented.
- This document is design-only and does not change runtime behavior.

## Problem

A user repository may want CI validation for `spec-injector` configuration and workflow expectations.

Possible reasons:

- Users may want to validate `.spec-injector/config.json` in pull requests.
- Users may want to ensure `spec validate` passes.
- An AI implementer may modify config or `always_read`, and CI can provide a guard.
- Larger teams may want consistent `spec-injector` workflow usage.

The risks are significant:

- Every repository has a different CI stack.
- Package manager, language, and monorepo structure differ across repositories.
- Automatically adding GitHub Actions can interfere with existing CI.
- Automatically setting branch protection required checks is even riskier.
- `spec-injector` cannot assume every repository uses Node.js.
- `spec-injector` cannot assume every repository wants a `spec-injector` check.

## Design principles

- Opt-in only.
- Never generated by default `spec init`.
- Explicit user approval required before writing `.github/workflows`.
- Generated workflow should be minimal.
- Scaffold should be inspectable before writing.
- Dry-run or preview should be available before mutation.
- Should not alter branch protection automatically in the first version.
- Should not assume the target repository package manager.
- Should validate `spec-injector` config, not replace project CI.
- Should not block normal `spec-injector` usage if scaffold is absent.

## Candidate user flows

### Option A: spec init --with-ci

Future candidate, not implemented:

    spec init --repo . --with-ci

Pros:

- Easy onboarding.
- One command initializes config and CI scaffold.

Cons:

- `init` becomes more invasive.
- Harder to separate config setup from CI setup.
- Users may not realize `.github/workflows` will be modified.

### Option B: spec workflow install github-actions

Future candidate, not implemented:

    spec workflow install github-actions --repo .

Pros:

- Explicit workflow installation.
- Better separation from `spec init`.
- Easier to preview and confirm.
- Can support future workflow types.

Cons:

- Requires a new command namespace.
- Adds more concepts for users.

### Recommendation

The first future implementation should prefer Option B:

    spec workflow install github-actions --repo .

Reasons:

- Clearer opt-in boundary.
- Avoids making `spec init` invasive.
- Aligns with the Layer 2 workflow scaffold direction.
- Easier to support preview/dry-run.

This issue does not implement the command.

## Candidate generated workflow

The following is a future candidate only. It is not an actual workflow file created by this issue.

    name: spec-injector

    on:
      pull_request:
      push:
        branches:
          - main

    jobs:
      validate:
        runs-on: ubuntu-latest

        steps:
          - name: Checkout
            uses: actions/checkout@v4

          - name: Setup Node
            uses: actions/setup-node@v4
            with:
              node-version: 24

          - name: Enable Corepack
            run: corepack enable

          - name: Install spec-injector
            run: pnpm add --global github:Erick52106/spec-injector

          - name: Validate spec-injector config
            run: spec validate --repo .

Important:

- This is only a future candidate.
- The GitHub install path is not formally supported yet.
- It may need to become a local action, npm beta install, or pinned version install.
- This issue should not create `.github/workflows/spec-injector.yml`.

## What should CI validate?

First-version candidates:

- `spec validate --repo .`
- Maybe `spec config suggest always-read --repo .` as informational only.

The first version should not run:

- `spec plan <issue>`, because it requires GitHub issue context.
- Branch protection changes.
- Automatic `always_read` mutation.
- AI-assisted setup.
- npm publish or release checks.
- Project-specific build/test commands.

## Preview / dry-run requirement

If `workflow install` is implemented in the future, it should provide preview:

    spec workflow install github-actions --repo . --dry-run

Or an equivalent mechanism.

Preview should show:

- Target file path.
- Exact workflow content.
- Whether the file already exists.
- What will be overwritten or refused.
- Next steps for the user.

## Overwrite policy

Future policy:

- If `.github/workflows/spec-injector.yml` does not exist, create it.
- If `.github/workflows/spec-injector.yml` exists, refuse by default.
- Require explicit `--force` to overwrite.
- Show a diff or summary before overwrite.
- Do not modify other workflow files.
- Never edit arbitrary existing CI files in the first version.

## Branch protection

The first version should not automatically configure branch protection.

Reasons:

- Required check names and GitHub Actions app/check-run behavior are easy to confuse.
- Repository permissions differ.
- Users may already have policies.
- Automatically changing protection can unexpectedly block users.

Future issues may discuss:

- `spec workflow protect main`
- GitHub API setup.
- Required check detection.
- Admin bypass policy.

## AI implementer guidance

When asked to install CI scaffold:

- Do not assume `spec init` should write GitHub Actions.
- Ask for approval before creating `.github/workflows/spec-injector.yml`.
- Prefer dry-run / preview first.
- Do not modify existing workflow files unless explicitly requested.
- Do not configure branch protection automatically.
- Explain that generated CI validates `spec-injector` config only, not the whole project.
- If install strategy is not stable, stop and report before writing workflow.

- Do not modify `spec init`.
- Do not modify branch protection.
